01 · modules/networking/main.tf, security_group.tf, bastion.tf, kms.tf

네트워크 경계 — VPC와 보안그룹

VPC(10.0.0.0/16)를 Public·Private·DB 3단으로 분리했다. DB 서브넷의 라우트 테이블에는 인터넷으로 나가는 경로 자체가 없다 — Aurora/Redis/DMS는 구조적으로 인터넷에 직접 노출될 수 없다.

보안그룹 5개를 최소 권한으로 체이닝했다: ALB(prod는 CloudFront prefix list만) → EKS(ALB SG에서 오는 트래픽만) → Aurora/Redis SG(EKS·Bastion·DMS SG에서만, 그 외 전부 차단) — Redis 서비스 자체는 DB 파트 담당이고, 여기서 다루는 건 그 앞단 경계뿐이다. 여기에 더해 KMS 키도 Aurora/S3/Redis 용도별로 분리해 로테이션을 켜뒀다.

Bastion — 인바운드 자체가 없는 운영 접점

DB 서브넷은 인터넷 경로가 없으니, 운영자가 Aurora/Redis에 붙으려면 Bastion을 거쳐야 한다. 이 Bastion에 SSH 포트(22)는 아예 열지 않았다 — 인바운드 규칙 자체가 없고, SSM Session Manager로만 접속한다. IAM Role도 AmazonSSMManagedInstanceCore 하나만 붙어있어서, 키 페어 분실이나 22번 포트 스캐닝으로 뚫릴 여지 자체를 없앴다.

EKS 클러스터 접근 권한

운영 접근을 이렇게 좁힌 김에, 클러스터 관리 권한도 다시 봤다. 원래 EKS Access Entry가 계정 root ARN에 클러스터 admin을 통짜로 부여하고 있었다 — 이 계정의 어떤 IAM 주체든 클러스터 전체를 관리할 수 있는 상태였다는 뜻이다. 이걸 eks_admin_principal_arns 변수로 바꿔서, 지정한 팀원 IAM ARN만 admin 권한을 갖도록 좁혔다.

02 · modules/networking/{route53,acm,cloudfront,waf}.tf · modules/infra/{cdn,eks-cluster}/*

엣지 — Route53, CloudFront, ALB, WAF

엣지에 있는 네 개 컴포넌트를 각각 설계했다. 그중 Route53과 ALB가 서로 부딪히는 지점에서 트러블슈팅이 있었는데, 그 과정은 따로 아래에서 다룬다.

Route53 / DNS

team-train.cloud 존 기준으로 main/www 레코드(CloudFront alias), db 레코드(Aurora CNAME), ACM 인증서 DNS 검증 레코드를 관리한다. api.team-train.cloud는 Primary(ALB) /Secondary(Azure App Service) Failover 레코드로 — 콘솔 수동 관리이던 걸 이번 세션에 Terraform 리소스로 전환했다.

modules/networking/route53.tfdomain/main.tf

CloudFront

S3 프론트엔드와 ALB 백엔드를 하나의 배포로 묶고, /api/* 경로만 ALB로 라우팅한다. 오리진에 시크릿 커스텀 헤더(X-Origin-Verify)를 심어서, ALB 쪽에서 "내 CloudFront 배포가 보낸 게 맞는지"까지 검증할 수 있게 했다 (아래 WAF·ALB 항목과 연결됨).

ALB 접근 제어

보안그룹은 CloudFront managed prefix list로만 인바운드를 연다 — WAF 우회 차단이 목적이다. HTTPS 리스너 기본 동작은 403이고, CloudFront가 심어준 커스텀 헤더가 일치하는 요청만 리스너 규칙에서 타겟그룹으로 forward된다.

WAF — 2단 방어

CloudFront 앞단(Common/SQLi 관리형 룰 + Rate Limit + IP 차단 리스트)과 ALB 앞단(같은 기준의 Regional WAF) 두 군데에 각각 붙였다. CloudFront WAF는 CloudFront 경유 트래픽만 보기 때문에, 커스텀 헤더 검증까지 뚫리는 경우를 대비해 ALB 쪽에도 별도로 필요했다.

트러블슈팅 — Route53 Failover가 계속 실패했다

증상 — ALB는 정상인데 Route53 헬스체크가 항상 Failure로 떴다. Primary가 멀쩡해도 Route53 입장에서는 죽은 것처럼 보이니 Failover가 오작동했다.

원인 — ALB는 CloudFront만 봐야 하는데, Route53 Failover는 ALB를 직접 봐야 한다는 게 문제였다. Route53이 Primary 생사를 확인하려면 ALB에 실제로 요청을 보내야 하는데, Route53 헬스체커의 IP 대역은 CloudFront prefix list에 없다. 그래서 헬스체크 트래픽 자체가 SG에서 그대로 막히고 있었다.

원인을 파다 보니 두 번째 허점도 나왔다 — prefix list는 "CloudFront에서 왔는지"만 확인하지, "내 CloudFront 배포에서 왔는지"는 확인하지 않는다. CloudFront IP 대역은 AWS의 모든 고객이 공유하므로, 제3자가 자기 CloudFront 배포의 오리진을 우리 ALB로 등록해도 SG는 그대로 통과시킨다.

검토한 해결책

대안여부이유
ALB SG에 Route53 헬스체커 IP 허용 기각 AWS가 managed prefix list로 제공 안 함. ip-ranges.json에서 직접 뽑아 관리해야 하는데 대역이 주기적으로 바뀌어 자동 갱신 파이프라인이 별도로 필요함
Route53 Primary를 CloudFront 도메인으로 변경 기각 CloudFront의 ALB 오리진 도메인이 api.team-train.cloud 자기 자신이라, Primary를 CloudFront로 돌리면 순환 참조가 생김
HealthyHostCount → CloudWatch 알람 → Route53이 알람만 조회 채택 네트워크 트래픽 없이 AWS 제어 영역 API로만 상태를 가져와서 SG 규칙과 완전히 무관하게 동작함

종합 — 위 네 가지가 겹쳐서 만드는 3단 방어

prefix list(SG, 방어선 1)는 그대로 두고 대체하지 않았다 — 대신 커스텀 헤더 검증(방어선 2)과 ALB Regional WAF(방어선 3)를 그 위에 얹었다. 헬스체크는 이 SG 규칙과 무관하게 CloudWatch 알람을 거쳐 동작하도록 따로 설계했다.

03 · modules/database/aurora_mysql.tf · modules/networking/iam.tf

자격증명 관리 — Secrets Manager

DB 자격증명이 코드나 tfvars에 평문으로 남지 않도록, Aurora 생성 직후 Secrets Manager에 DB_USER/DB_PASSWORD/DB_HOST/DB_NAME을 저장하고, 이걸 읽어갈 수 있는 IAM 정책을 secret:team-train-db-* 패턴으로 특정 시크릿에만 스코프했다 — 계정 내 다른 시크릿에는 접근 못 하게.

순환 참조 문제도 있었다 — Secrets Manager 리소스가 database 모듈과 networking 모듈 양쪽에서 필요해서, 시크릿 생성은 database 모듈에 두고 IAM 정책만 networking 모듈에서 관리하는 식으로 의존성 방향을 한 방향으로 정리했다.

IRSA — 노드가 아니라 파드 단위로 권한을 준다

위 IAM 정책은 노드의 EC2 Role이 아니라 IRSA(IAM Roles for Service Accounts)로 pod에 붙는다는 전제로 설계했다. EKS OIDC 프로바이더를 신뢰하는 Role의 조건절에 system:serviceaccount:default:booking-sa처럼 특정 K8s ServiceAccount 하나만 명시하면, 그 파드만 이 정책을 쓸 수 있다. 노드 Role에 전부 묶어두면 같은 노드에 뜨는 다른 파드도 그 권한을 같이 쓸 수 있게 되는데, IRSA는 그 문제를 파드 단위로 끊는다 — 시크릿 정책을 설계할 때 이 경계를 기준으로 삼았다.

04 · modules/networking/cloudtrail.tf · modules/infra/logging/athena.tf

감사·탐지 — CloudTrail

전 리전 CloudTrail을 KMS 암호화된 S3에 저장하고 로그 무결성 검증을 켰다. 여기에 실시간 탐지 계층을 추가했다 — CloudWatch Logs로 이중 전송하고, 루트 계정 사용 · IAM 정책 변경 · 보안그룹 변경 · CloudTrail 자체 조작 네 가지를 Metric Filter + Alarm으로 감시한다. 그중 CloudTrail 자체 조작 (StopLogging/DeleteTrail)은 공격자가 흔적을 지울 때 제일 먼저 노리는 지점이라 따로 넣었다.

탐지뿐 아니라 사후 조회 쪽도 손봤다 — 로그 조회용 Glue Crawler는 제거했다. CloudTrail 로그는 스키마가 고정돼있어 크롤러로 "추론"할 필요가 없다 — 대신 파티션 프로젝션 기반 Athena 테이블로 바꿔서, 크롤러 스케줄 실행이나 MSCK REPAIR TABLE 없이도 항상 최신 파티션이 조회되게 했다.

05 · modules/networking/vpn.tf · modules/azure-networking · modules/database/dms.tf

멀티클라우드 DR — Azure Site-to-Site VPN

Aurora → Azure MySQL로의 DR 복제(DMS)가 공개 인터넷이 아니라 AWS↔Azure 사설 IPSec 터널을 타도록 VPN Gateway·Customer Gateway를 연동했다. DMS 보안그룹의 아웃바운드도 0.0.0.0/0이 아니라 Azure VNet CIDR로만 제한된다.

Azure VPN Gateway의 공개 IP는 Azure 쪽을 먼저 apply해야 알 수 있다는 순서 문제가 있어서, 2단계 apply로 설계했다 — 1단계는 IP 없이(리소스 count=0으로 대기) Azure 쪽만 먼저 만들고, 확보된 IP를 변수로 넣어 2단계에서 AWS VPN 리소스를 실제로 생성한다.

여기서 끝내지 않고 실제로 한 번 배포해서 확인했다 — Aurora에서 Azure MySQL로 복제가 붙는 것, 터널이 사설 구간에서 암호화된 채로 유지되는 것, 그리고 DR 전환 시나리오대로 Azure 쪽으로 넘어가는 것까지 직접 검증했다.

→ 딥다이브: AWS와 Azure가 서로의 IP를 몰라야 배포가 안 되는 상황 — 2단계 apply로 푼 순환 참조
