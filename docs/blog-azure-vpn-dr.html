AWS와 Azure가 서로의 IP를 몰라야 배포가 안 되는 상황 — 2단계 apply로 푼 순환 참조

배경

Aurora가 완전히 죽는 상황(AWS 리전 장애 등)까지 대비하려면 다른 클라우드에 복제본이 있어야 한다는 결론이 나왔다. 그래서 DMS로 Aurora MySQL을 Azure MySQL로 실시간 복제(full-load-and-cdc)하는 DR 경로를 만들었다. 조건이 하나 있었다 — 이 복제 트래픽이 공개 인터넷을 타면 안 된다는 것. DB 자격증명과 실제 데이터가 오가는 경로인데 인터넷 구간을 거치게 둘 수는 없었다. 그래서 AWS VPC와 Azure VNet 사이에 Site-to-Site VPN을 놓기로 했다.

문제 — 둘 다 서로를 먼저 알아야 한다

AWS 쪽 aws_customer_gateway는 Azure VPN Gateway의 공개 IP를 알아야 만들어진다. Azure 쪽 azurerm_local_network_gateway(AWS를 가리키는 게이트웨이)는 AWS VPN Connection이 만들어준 터널 주소를 알아야 만들어진다.

즉:

  • AWS 리소스를 완성하려면 Azure의 출력값이 필요하고
  • Azure 리소스를 완성하려면 AWS의 출력값이 필요하다

한 번의 terraform apply로는 원천적으로 안 풀리는 구조다. 두 클라우드, 두 개의 별도 state를 쓰는 상황에서는 더더욱 그렇다.

해결 — 2단계로 쪼갠다

순서를 이렇게 나눴다.

1단계 — Azure 쪽만 먼저 apply한다. azurerm_virtual_network_gateway를 만들면 30~45분 뒤 공개 IP가 나온다. 이 시점에는 AWS를 가리키는 Azure의 LNG/Connection 리소스는 만들지 않는다 — count = var.aws_vpn_tunnel1_address != "" ? 1 : 0로 게이팅해서, AWS 쪽 정보가 없으면 아예 생성 자체를 건너뛴다.

2단계 — 1단계에서 나온 Azure 공개 IP를 AWS networking 모듈의 azure_vpn_gateway_ip 변수에 넣고 전체를 다시 apply한다. 그러면 AWS aws_vpn_connection이 만들어지면서 터널 주소(tunnel1/tunnel2)가 나온다. 이 값을 다시 Azure 모듈의 변수에 넣으면, 아까 count=0으로 막아뒀던 Azure LNG/Connection이 그제서야 생성된다.

닭이 먼저냐 달걀이 먼저냐를, "먼저 낳을 수 있는 만큼만 낳고, 그 결과로 나머지를 낳는다"는 식으로 두 번에 나눠 처리한 셈이다. Terraform 안에서 자동으로 풀 방법은 없었다 — count 게이팅 + 변수 주입 + 2회 apply가 이 구조에서 가장 단순한 해법이었다.

이중화 — Azure는 BGP가 없다

AWS VPN Connection은 기본으로 터널을 2개(tunnel1, tunnel2) 만들어준다. 근데 이걸 그대로 이중화로 쓰려면 Azure 쪽에서 두 터널을 하나의 연결처럼 다뤄야 하는데, 이번 구성은 static_routes_only = true — BGP 없는 정적 라우팅이다. BGP가 없으면 Azure Local Network Gateway 하나가 두 터널을 동적으로 넘나들 수 없다.

그래서 터널마다 별도의 azurerm_local_network_gateway와 azurerm_virtual_network_gateway_connection을 만들어서, 같은 Azure VPN Gateway에 두 개의 독립된 연결로 붙였다. 터널 1이 죽어도 터널 2로 만든 별도 연결이 살아있으니 그쪽으로 우회된다 — BGP 없이 이중화를 만드는 방법이 "연결 자체를 두 개 만드는 것"이었다.

라우팅 — 우선순위를 규칙 순서가 아니라 prefix 길이로 해결

Private/DB 서브넷의 라우트 테이블에는 이미 0.0.0.0/0 → NAT Gateway 라우트가 있다. 여기에 <Azure VNet CIDR> → VGW 라우트를 추가로 얹었는데, 둘 다 "동시에 매치 가능한" 상태가 된다. 이때 어느 라우트를 탈지는 규칙을 넣은 순서가 아니라 더 구체적인(prefix가 긴) 라우트가 우선한다는 라우팅 테이블의 기본 동작으로 정리된다. 0.0.0.0/0보다 Azure CIDR 쪽이 항상 더 구체적이므로, Azure로 가는 트래픽만 자동으로 VGW를 타고 나머지는 그대로 NAT Gateway로 나간다 — 별도 라우팅 우선순위 설정이 필요 없었다.

DMS 쪽 설계

  • multi_az = true로 복제 인스턴스를 두 AZ에 걸쳐 배치했다. AZ 하나가 죽어도 반대 AZ의 Standby로 자동 페일오버된다. 두 AZ가 동시에 죽는(AWS 리전 자체 장애) 경우에만 Azure MySQL로 수동 전환하는 게 이 설계의 마지막 방어선이다.
  • migration_type = "full-load-and-cdc" — 최초 전체 복사 후 실시간 CDC로 이어 붙인다. Aurora 쪽 부하를 고려해 처음부터 CDC만 켜지 않고 풀로드를 먼저 태웠다.
  • dev 환경에서는 DMS를 아예 안 만든다(dms_enabled = var.environment == "prod" && ...) — DMS가 쓰는 dms-vpc-role 같은 IAM 리소스가 계정 전역이라, 환경별로 중복 생성하면 충돌한다.

실제로 검증한 것

설계 문서로만 남기지 않았다. 실제로 1단계·2단계 apply를 순서대로 실행해서 Azure VPN Gateway가 뜨는 것, AWS-Azure 터널이 맺어지는 것, Aurora에서 Azure MySQL로 복제가 실제로 붙는 것까지 확인했다. 이 프로젝트에서 유일하게 "설계 → 배포 → 실측"까지 전체 사이클을 다 돌려본 부분이다.

트레이드오프

  • 정적 라우팅(BGP 없음)이라 터널 장애 시 경로 전환이 동적으로 재계산되지 않는다 — 위에서 말한 이중 연결 구조로 대신했지만, BGP 기반 라우팅만큼 유연하지는 않다.
  • 2단계 apply는 사람이 중간에 개입해서 변수를 갈아끼워야 한다. 원클릭으로 안 끝나고, CI 파이프라인에 태우려면 이 부분만 별도 처리(예: 1단계 apply 후 output을 가져와 2단계 tfvars에 자동 주입하는 스크립트)가 추가로 필요하다. 지금은 수동으로 두 번 돌리는 것으로 충분하다고 판단했다.
  • Azure MySQL 엔드포인트는 VNet 내부 사설 FQDN이라, DMS 타겟 엔드포인트가 이 사설 이름을 그대로 못 쓰면(연결 실패 시) VPN 터널 자체의 DNS 전파를 의심해봐야 한다 — 이 부분은 트러블슈팅 여지가 아직 남아있다.

마무리

두 시스템이 서로를 완성하기 위해 서로의 결과물을 기다려야 하는 상황은 IaC에서 은근히 자주 나온다. 이번엔 그걸 "한 번에 다 풀려는 시도"를 접고, 풀 수 있는 절반만 먼저 만들고 그 결과로 나머지 절반을 만드는 순서로 쪼갠 게 핵심이었다. Terraform의 count 게이팅이 이런 단계적 배포를 표현하기에 생각보다 잘 맞았다.
